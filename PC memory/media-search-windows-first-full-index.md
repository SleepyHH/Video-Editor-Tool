Ran the step-2 media search indexer (`media_index.py`) against the shared external drive from the Windows PC for the first time ever, 06/07-08-2026 — this was also the first real exercise of the Windows code paths in [[media-search-shared-drive-architecture]] and [[media-search-mode-a-spec]]. Result: **complete**, 18,724 files scanned, 14,591 indexed, 88,177 frames/images embedded. Along the way, found and fixed five real bugs (live, not theoretical) plus one operational lesson worth carrying forward.

**Bugs found and fixed in `media_index.py`/`config.py`:**

1. **Windows iCloud cloud-placeholder files hang indefinitely, not just error.** A file can appear in a normal directory listing with a real size but not actually be downloaded (`attrib` shows the `O`/Offline flag). `Image.open()` on one of these doesn't raise - it blocks forever waiting on an on-demand cloud recall that can stall. This silently killed a full run. Fixed with `_is_windows_cloud_placeholder()` (checks `FILE_ATTRIBUTE_OFFLINE`/`RECALL_ON_OPEN`/`RECALL_ON_DATA_ACCESS` via `GetFileAttributesW`), applied before opening any file in both the local iCloud-folder scan and the external-drive walk. No-op on Mac.
2. **ffmpeg was 100% CPU software-decoding video despite hardware decode being available.** The Windows ffmpeg build (gyan.dev full_build) has NVDEC/cuvid compiled in and the PC has an RTX 4060, but nothing requested `-hwaccel`. Fixed via `profile["ffmpeg_hwaccel"] = "cuda"` on Windows (`None` on Mac - can't verify the bundled Mac ffmpeg binary has videotoolbox support, so left unchanged there), with automatic fallback to software decode if the hardware path errors on a given file.
3. **No timeout anywhere on ffmpeg subprocess calls.** A single pathological file could hang the whole unattended multi-hour run forever with zero error. Added `timeout=120` (metadata read) / `timeout=300` (frame extraction).
4. **CUDA OOM cascade - the serious one.** `embed_images()` batched an *entire video's* frames into one single GPU forward pass with no cap. At the new 1s sampling interval (see below), a long/high-res video produced a batch too large for the 8GB card, triggering a real CUDA out-of-memory error - and once that happens, the CUDA context is corrupted for the rest of the process, so *every subsequent file* failed identically (silently, no crash) until the process was killed and restarted. Confirmed live: this wasted ~1,700 files' worth of GPU time before being caught. Fixed with `EMBED_BATCH_SIZE = 32` - `embed_images()` now processes in capped chunks regardless of source video length.
5. **Index self-pollution.** The external-drive walk recursed into the index's own `HuysVideoEditor_SearchIndex/thumbnails/` cache folder and indexed the generated thumbnails as if they were separate library photos - would have grown worse every time someone browsed search results. Fixed by adding `"HuysVideoEditor_SearchIndex"` to `IGNORED_DIR_NAMES`. Cleaned up the handful of already-polluted rows.

**Frame interval changed 5s → 1s** (user request, 06-08-2026) at `FRAME_INTERVAL_SECONDS` in `media_index.py`. Since the incremental skip logic only keys on path+mtime, there was no way to tell "already indexed at old density" from "correctly indexed at new density" apart - added a `frame_interval_seconds` column to `indexed_files` (populated for every video row going forward) plus a new `force_reembed_stale_videos()` function that finds video rows whose recorded interval doesn't match the current constant, deletes their old vectors, and **compacts + renumbers** the embeddings array (`vector_index` is a direct row-position pointer into `embeddings.npy` per `media_search.search`, so a naive delete without renumbering would silently corrupt every later lookup). Reconciled this run's own history against the log of the very first (session-restart-killed) run to correctly identify which legacy rows were already-correct vs. genuinely stale, avoiding needless re-embedding of ~578 already-correct videos.

**Known remaining gap:** 20 legacy video rows were from the Mac's native Photos library (pre-shared-drive baseline, plain Mac-absolute paths) - correctly force-cleared of their stale 5s data, but Windows has no way to re-embed them (can't see Mac-native paths at all, `pipeline_mode` there is `cloud` not `native_db`). Will resolve automatically next time `build_index()` runs on the Mac - no action needed beyond that.

**Operational lesson - detached processes for long unattended jobs:** a background job launched through the normal harness-tracked mechanism died when the Claude Code session itself restarted, silently, mid-run. For anything expected to run unattended for hours, launch as a genuinely detached OS process instead: PowerShell `Start-Process -WindowStyle Hidden -RedirectStandardOutput <log>` (on Mac: `nohup ... &` or similar), so it survives independent of the assistant's own session lifecycle. Still needs periodic manual/scheduled checks since nothing then reports completion automatically.

**How to apply:** when next indexing on the Mac (or recalibrating frame interval again), these fixes should already be in the shared `media_index.py`/`config.py` (synced via OneDrive) - no need to re-derive them. If frame interval changes again, `force_reembed_stale_videos()` handles it correctly on its own. If a long run needs to survive a session restart, use the detached-process pattern above.
