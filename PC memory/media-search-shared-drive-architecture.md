Confirmed 2026-08-05/06: the user has an external drive ("Huy's HDD", exFAT, found via `config.find_volume_by_label`) holding their actual media-to-edit library, used from both this Mac and a Windows PC (one internal drive, NVIDIA GTX 4060 GPU, OneDrive + Obsidian already syncing there). The index is now genuinely shared between machines, not rebuilt separately per machine:

- **Index location**: `media_index.get_index_dir()` (and `get_embeddings_path()`/`get_db_path()`) point at `<drive>/HuysVideoEditor_SearchIndex/` whenever the drive is connected, falling back to the original `~/Documents/HuysVideoEditor_SearchIndex/` otherwise. These are functions, not fixed constants, since drive availability changes between runs - every module that needs these paths calls the function fresh rather than importing a stale module-level path.
- **Portable paths**: a stored absolute path like `/Volumes/Huy's HDD/italy/video.mov` is Mac-specific and would be wrong the instant it's read from Windows (`E:\italy\video.mov` or similar). `config.to_portable_path()`/`resolve_portable_path()` store drive-sourced files as `DRIVE::relative/path` instead, resolved back to a real path on whichever machine is currently running via `find_volume_by_label()`. Genuinely local-only content (the Mac's native Photos library, which has no PC equivalent) stays as a plain absolute path - unresolvable/skipped when read from the PC, which is correct, not a bug, since that content really isn't there.
- **A real bug, not a config choice**: this Mac's exFAT mount uses Apple's newer FSKit driver ("noowners" in the mount flags), which doesn't fully support the POSIX file locking SQLite's default journal mode needs - caused genuine "readonly database" write failures, confirmed live. Fixed with `PRAGMA locking_mode=EXCLUSIVE` in `media_index.init_db()`, which is the *correct* choice regardless of the bug, not just a workaround: this is a single-writer tool and a USB drive is only ever plugged into one machine at a time, so there's no real concurrent-write scenario to protect against anyway.
- **Real tradeoff from that fix**: the database can't be queried by a second process while indexing is actively writing to it (`database is locked`). Not a cross-machine issue (physically can't happen with one USB drive), just: don't run `media_search_server.py` and `media_index.py` against the same drive at the same time on one machine.
- **`TEMP_TEST_FOLDERS`** (`~/Documents/Photos back up`) was removed as a source entirely - confirmed via a full recursive filename comparison that all 4,502 of its files already exist inside a "Camera Roll" folder on the drive (which also has ~13k more files on top), so indexing both would have double-embedded the same photos under two different paths.
- **Migration note**: the pre-shared-drive index (Mac-only, absolute paths, included the now-removed Photos-back-up content) was archived rather than migrated, at `~/Documents/HuysVideoEditor_SearchIndex_archived_pre-shared-index_05-08-26/` - not deleted, but not in active use. The shared drive index was rebuilt fresh instead of attempting a risky positional-array rewrite of the old one late at night.

**How to apply:** any function reading/writing `items.file_path` or `indexed_files.file_path` must go through `to_portable_path`/`resolve_portable_path` - never assume the stored value is a directly-usable absolute path. Any new raw `sqlite3.connect()` to this database needs the same `PRAGMA locking_mode=EXCLUSIVE` (or better, just call `media_index.init_db()` instead of connecting directly, which already applies it). See [[media-search-mode-a-spec]] for the original engine decisions this extends.

**Confirmed live on real Windows hardware, 06/07-08-2026** (previously just a code comment saying "unverified, no machine to test"): `find_volume_by_label` correctly resolves the drive as `D:\` via `GetVolumeInformationW`, and `DRIVE::`-portable paths written by the Mac resolve to real, existing files on the PC (`DRIVE::image.jpg` → `D:\image.jpg`, confirmed to exist). The cross-machine design genuinely works both directions, not just in theory. The drive itself is a **WD Elements 2621, a real mechanical HDD over USB** (not SSD) - worth remembering as a real bottleneck for anything indexing-speed-related. Full first-index-run details (bugs found/fixed, throughput) in [[media-search-windows-first-full-index]].
